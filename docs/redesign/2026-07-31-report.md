# UI/UX redesign pass — what changed and what is left

Branch `claude/macos-app-redesign-37c0a2`, on top of `679495a`. Nothing is pushed.

The audit that preceded this is [2026-07-31-audit.md](2026-07-31-audit.md). Read that first: four and a half of
its twenty-five findings were withdrawn during the work, and *why* they were withdrawn is more useful
than the findings that survived.

---

## The constraint this ran under, and why it shaped everything

The machine's screen was locked for the entire session. That has three consequences worth stating
plainly, because they bound what can be claimed:

1. **Nothing could be clicked.** No synthetic keystroke or activation reaches an application while
   the login window holds focus. Every screen in this report was reached by *launching* the app onto
   it, which is why the first commit adds the arguments that make that possible.
2. **Every capture is of an inactive window.** macOS desaturates accent colour, flattens
   `.borderedProminent` fills, and drops the accent from a selected row when the app is not frontmost.
   **No claim in this report is about accent colour, selection appearance, or button prominence** —
   one finding was recorded on that basis and then withdrawn. Those need a person.
3. **Capture needs the display lit.** ScreenCaptureKit refuses while it is asleep, so the sweeps woke
   it in bursts. Your lock screen came on a number of times overnight.

What the captures *are* reliable for is everything geometric and typographic: widths, truncation, row
heights, spacing, alignment, which glyphs appear, and what the copy says. Every surviving finding and
every claim below is of that kind.

## What the tooling now makes possible

Four development-only launch arguments, all gated on `-ElephruitDevelopmentMode`:

```bash
open -n "$BUILT_PRODUCTS_DIR/Elephruit.app" --args \
  -ElephruitDevelopmentMode -ElephruitUseTemporaryStore \
  -ElephruitUseFixtureCalendar -ElephruitUseFixtureContacts -ElephruitUseFixtureReminders \
  -ElephruitFixturesAuthorized -ElephruitLoadSampleData -ElephruitPeopleCount 400 \
  -ElephruitStartModule people -ElephruitAppearance dark -ElephruitWindowSize 1180x760
```

| Argument | What it unblocks |
|---|---|
| `-ElephruitStartModule` | Opens onto any module or destination, overriding scene restoration |
| `-ElephruitAppearance` | Forces light or dark **for this process only** — your other windows are untouched |
| `-ElephruitWindowSize` | Makes a narrow-window review repeatable rather than a matter of dragging an edge |
| `-ElephruitFixturesAuthorized` | Starts the synthetic calendar, address book and Reminders already granted |
| `-ElephruitLoadSampleData` | Plants the sample library into an empty one |
| `-ElephruitPeopleCount` | Tops People up to a given number of invented records |

Two of these paid for themselves immediately, and it is worth being blunt about how.

**The calendar module had never been photographed in a working state**, in this project's whole
history, because the fixture provider starts at `.notRequested` and reaching "authorized" meant a
human clicking Allow. The README recorded that gap across several sessions. It is now closed.

**The fixture store persists between runs**, so the normal state is a library planted by an *older
build*. This audit recorded a `promise` tag as a live defect on exactly that basis — the source had
written `follow-up` since the previous pass, and the tag was simply left over. A review that cannot
re-plant the library from the build in front of it reports the last build's bugs.

**Eight people cannot demonstrate a scrolling problem or its absence.** Seeding to 400 withdrew two
more findings on the spot: the A–Z index is a jump bar distributing the alphabet evenly, exactly as
Contacts does, and only looked broken because eight records could not fill it; and the row height
recorded by the previous pass as "~80, near twice what it needs" is 52 against a 44-point token — the
earlier figure counted a section header as part of the row.

## The design decisions

### A row's date is the one that matters for the state the item is in

`RowDate` states it once: the deletion in the Trash, the archiving in the Archive, the deadline where
there is one, otherwise when it last changed. Three consequences follow from having a rule rather
than a field:

- **Notes have dates at all now.** The row showed `dueAt`, and a note has no deadline, so the one
  list where "when did I last touch this" is the entire question was the one list answering nothing.
- **Only a deadline is coloured by lateness.** Lateness is a property of an obligation. "Edited
  yesterday" drawn in red is the interface inventing one.
- **Only the two surprising dates carry a word.** A deadline needs no prefix (every task application
  shares that convention) and neither does a last-edited date (Finder and Notes share that one).
  Spelling out "Edited" on every row cost about a third of a list column to repeat something that was
  identical all the way down. "Deleted" and "Archived" stay, because "3 Jul" beside a deleted note is
  a date with no question attached.

The row's **accessibility label reads from the same rule**. It did not before, and the gap widened
the moment the row learned to show an edit date: the list was fully dated for anybody looking at it
and undated for anybody listening. The label also carries what the screen drops — a bare date tells a
deadline from a last edit by colour and by the row's glyph, and neither reaches VoiceOver.

### A row's width belongs to the thing the row is for

Tags, a priority mark and a date used to share the title's line and took a fixed ~150 points off a
column about 330 wide, which is why a list of notes read "Migration runb…", "Positionin…". Only the
title and the one date share that line now; everything else drops to the second line, which had room
to spare. The right-hand edge reads as a single metadata column rather than two ragged ones.

Widening the column was tried first and is the better fix in principle. See *Remaining issues*.

### An empty state says what *it* is empty of

One sentence — "Choose something from the list, or press ⌘N to make something new" — was the detail
pane's answer in eleven destinations, and it was written for one. In the Trash it instructs you to
create something in the wastebasket, and ⌘N there does something worse than nothing: it silently
leaves the Trash and starts a note elsewhere. The rule now is that a shortcut is named only where it
does the thing the sentence implies — a hint needing a footnote is not a hint.

### A colour comes from the palette, and the test now checks that

`SourceHygieneTests` enforced "no view names a literal colour" and the README rested a dark-mode
guarantee on it. It looked only for *numeric* constructors, so SwiftUI's named colours had
accumulated to twenty-four uses across six files. Most were not bugs — named hues adapt — but they
were nine independent spellings of "capture is purple" and three of "a child's details are pink".
`Color.white` was the one that is simply wrong: it does not adapt at all, and it was drawing text on
fills that go pale under Increase Contrast and at the low end of an intensity scale.

New tokens: `Theme.Colors.onAccent`, `.captureAccent`, `.familyAccent`. The test now catches named
colours too.

## Builds and tests

- `xcodebuild … -configuration Debug build` — succeeds, zero warnings, after every commit.
- `xcodebuild … -configuration Release build` — succeeds, zero warnings.
- `swift test` — **1,823 tests**, up from 1,693. All pass **except one**, described below.
- 43 tests added: the launch-argument parser, the row-date rule, the empty-state copy, and the
  column-width arithmetic across all seven document modules.
- **Benchmarks: not run.** `ELEPHRUIT_BENCHMARKS=1 swift test --filter Benchmark` was started and
  produced no output after fifty minutes against a documented runtime of under ten seconds, so I
  stopped it rather than leave it running on your machine overnight. Whether that is a hang or a
  filter matching more than the reduced corpus, I did not diagnose. **No performance claim in this
  report rests on a measurement** — the argument that the row work is free is that it is layout-only
  (`lineLimit`, `fixedSize`, `layoutPriority`, one extra `Text`), with no allocation and no
  measurement pass, and `ViewThatFits` was again kept out of the People list. That is an argument,
  not a number, and the People list at 400 records is on the QA checklist for that reason.

### One test fails, and it is not from this branch

`PersonActionAvailabilityTests` → "One number is named; several say a choice is coming" expects
`"mobile · 512-555-0192"`. **It fails identically at `679495a`**, verified in a scratch worktree. It
is untouched here: whether the phone formatter moved or the expectation did is not a question this
pass can answer, and guessing would have hidden it.

## Remaining issues, ranked

1. **AppKit will not give the middle column the width the shell asks for.** This is the deepest
   finding of the pass and it is *not fixed*. `ModuleShellLayout.widths(…)` now computes correctly —
   seven modules are asserted to reach their declared ceiling and to leave nothing unallocated — and
   `applyModuleLayout` now pins what the shell worked out rather than a second, divergent answer from
   the store. The column is still laid out near its ideal on screen. `navigationSplitViewColumnWidth`
   is a request; the previous pass found the same wall from the other direction and enforced only the
   minimum, as the content's own frame. Enforcing the *resolved* width the same way would work and
   would make the divider un-draggable inward, because the frame would refuse the drag that the
   recorder needs to see in order to store a narrower width. It needs an `NSSplitView` delegate or a
   representable, and it is a piece of work rather than a tweak.
2. **The detail pane is a very large empty rectangle whenever nothing is selected.** Roughly 1,000
   points of it in a 1710-point window. The copy in it is now correct per destination; the *shape* of
   the problem is untouched, and it is the most visible thing left in the app.
3. **Four row layouts still exist.** This pass unified the shared `ItemRow`, which covers Today,
   Upcoming, Inbox, Notes, Projects, Areas, Bookmarks, Archive and Trash. **Tasks still draws its own
   row** with a second line of glyph-prefixed metadata, and People draws its own. Tasks is the one
   that matters: it shows the same objects as Today, differently, on adjacent screens.
4. **Today and Tasks disagree about the colour of a late date.** Today draws it red, Tasks amber.
   Both are deliberate: `TaskRow` argues its case in the source — *"the date is amber, not the row,
   and never red. Overdue is information about a date, and a red row is an accusation about a
   person"* — and I left it alone rather than overrule a stated position overnight. But the same task
   is red on one screen and amber on the next, and one of the two should give way. **This is a
   product decision for you, not a defect.** Note that neither relies on colour alone: "44 days late"
   and "Due today" differ in their words.
5. **Time shows every control twice.** The sidebar has Period and Grouped By; the toolbar has popups
   setting the same two properties, on screen simultaneously.
6. ~~**The person profile header is the least native surface in the app.**~~ **Now fixed** — see
   commit `5a161a3`, and [before](2026-07-31/before/person-profile-header.png) against
   [after](2026-07-31/after/person-profile-header.png). Three saturated pills in a shadowed floating
   card became ordinary macOS buttons with one accent-blue primary; the "Build a better mental
   picture" card is gone; the starter facts became `+`-prefixed bordered controls so an offer no
   longer renders identically to a record; the run-on identity line was split from the history line;
   and the explanatory subtitle under one section header was dropped.

   What is *not* fixed there: the Contact section still draws two envelope glyphs on one line, one as
   the type icon and one as the action.

7. **Relationship editing is now labelled, but unverified on screen.** It was an unlabelled `…` with
   only a tooltip. The relationship *type* is now the control — a capsule showing "partner" with a
   chevron — so the thing you would want to change looks like the thing you press, and the child card
   has a "Relationship" button rather than a glyph. Editing and deletion themselves were already
   sound. **I never saw the new control**: the sample person I could reach has their relationship
   rendered in the header subtitle rather than as a chip, so this needs your eye.
8. **"Start"/"Deadline" in the task detail pane vs "Defer until"/"Due" in the inspector beside it.**
   Unchanged from the previous pass's list.
9. **The Calendar window is titled "Elephruit"** while every other module is titled with its own name,
   and it carries a second toolbar row below the first.
10. **The search field renames itself** — "Search everything" in most modules, "Search People" in
   People.
11. **An empty "Calendar Sets" section header** is drawn with nothing beneath it.
12. **Unlabelled glyphs carry meaning**: a link symbol on every calendar row in Today, a sparkle in
    the Tasks toolbar, a currency glyph in the timer bar.
13. **Tag chips lose their boundary in dark mode** — `quaternarySystemFill` behind caption text on the
    dark list background.

## Manual QA checklist

The first two exist because the method could not cover them.

- [ ] **Look at the app while it is the active application.** Everything in this report was
      photographed inactive, so accent colour, selected-row appearance and prominent button fills were
      never seen. Check a selected row in a focused list, and the "Ask Again" button under Calendar's
      permission state.
- [ ] **Turn a calendar off in the Calendar sidebar and watch the checkmark.** The requirement is an
      immediate visible checked/unchecked state. Reading the code, `toggleVisibility` sets the
      observed property before its `await`, so it should be immediate — but it was never clicked.
- [ ] Notes: every row shows a date, and titles are whole where they fit.
- [ ] Trash: rows say "Deleted <date>"; the empty detail pane talks about putting things back and does
      **not** mention ⌘N.
- [ ] Archive: rows say "Archived <date>".
- [ ] ⌘1 goes to Inbox (it previously did nothing — Home was shadowing it). Home is now ⌥⌘H.
- [ ] Settings ▸ Advanced shows "Indexed items", "Distinct terms" and "State". These have never
      rendered before.
- [ ] Settings ▸ shortcut editor lists "Import Files…" rather than "Show Inspector" for ⌘⇧I.
- [ ] Drag the list/detail divider narrow in Today, Tasks and Notes. Chips and dates stay whole; only
      the title truncates.
- [ ] People with 400 records: scroll the full length. Use
      `-ElephruitLoadSampleData -ElephruitPeopleCount 400`.
- [ ] Dark mode **and Increase Contrast**, on the calendar month view, the time grid, the heatmap, a
      selected tag chip and a prominent contact button — the five places `Color.white` was replaced.
- [ ] VoiceOver over a notes list: each row should announce "edited …", which it never did before.
- [ ] A person with a relationship: the type ("partner", "sister") is now a capsule with a chevron
      that opens the edit-and-delete sheet, replacing an unlabelled `…`. I could not reach this on
      screen — please confirm it looks like a control and not like a tag.

## Two things I changed on your machine

- **`com.elephruit.Elephruit` preferences.** Both instances share a defaults domain, so my launches
  wrote `layout.moduleColumnWidths` and AppKit's split-view autosave all night, and I deleted both
  keys while testing whether the width policy takes effect on a fresh window. A backup taken before
  any of that is at `docs/redesign/2026-07-31/prefs-backup.plist`; restore with
  `defaults import com.elephruit.Elephruit <file>` if your window layout is not where you left it.
- **Nothing else.** Your real library was never opened by anything I ran — every launch used
  `-ElephruitUseTemporaryStore` and the fixture providers, addressed by process id so the Elephruit
  you had running from Xcode was never touched. No TCC permission was changed.
